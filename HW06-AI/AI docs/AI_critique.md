# AI Critique

The AI was useful for expanding a small specification into systematic domain partitions, boundary cases, security traces, JSON schemas, and an executable Postman collection. However, its first output was incomplete in two important ways. First, it emphasized isolated request-response cases and did not naturally prioritize cross-request behavior. Tests for OTP rotation, persistence after a rejected shipping cancellation, update isolation, and repeated deletion were added only after comparing the generated suite with my HW02/HW04 evidence. These cases require remembering state across several calls, which a prompt organized mainly around parameters and status codes tends to underweight. Second, the AI-generated test harness itself was wrong. It placed asynchronous setup calls in a Newman pre-request script using top-level `await`; after a syntax fix, Newman still sent the main request before the Promise completed. This produced misleading 401 failures. The mistake was found by examining the full execution report rather than accepting a large failure count as proof of SUT defects. I corrected the design so registration, login, state transitions, and fixture creation run as ordinary sequential Collection requests, then reran from a clean seeded database. The final run had zero setup or script failures, so the remaining failures could be triaged against the contract. The AI also proposed some status expectations more confidently than the specification justified, so I kept the specification as the oracle and grouped related symptoms instead of reporting every failed assertion as a separate bug. My main lesson is that collaborating with AI requires two independent reviews: validate the test oracle, and validate the test mechanism. High coverage is not credible when prerequisites, timing, variable scope, or evidence provenance are wrong. AI accelerates enumeration and automation, but the student must control state, audit assumptions, reproduce findings, and refuse fabricated evidence.
